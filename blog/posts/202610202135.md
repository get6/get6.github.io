[지난 글](/posts/202610181853)에서 에이전트가 일하는 걸 지켜보는 화면을 설계해봤다고 했죠. 그보다 앞선 2026년 3월에 남겨둔 메모가 하나 있어요. 실행 엔진을 직접 키우는 대신 **실행과 오케스트레이션은 Paperclip에 맡기고**, 우리는 Obsidian에서 문서를 쓰는 데 집중하자는 내용이었어요.

7개월이 지나는 동안 Paperclip도, 비슷한 자리를 노리는 Multica도 정말 많이 바뀌었어요. 두 도구 모두 거의 매주 릴리스를 내고 있거든요. 그래서 그때 세운 기준으로 두 도구를 처음부터 다시 비교해봤어요.

> 이 글의 수치와 기능은 **2026년 10월 20일** 기준이에요. 두 프로젝트 모두 변화가 빠르니, 도입 전에는 아래 참고 링크의 최신 changelog를 꼭 다시 확인해보세요.

## 3월 메모에서 세운 역할 분담

메모에서는 시스템을 세 역할로 나눴어요. 이번 비교도 이 세 가지를 기준으로 삼았어요.

1. **기획·문서화** — Obsidian에서 Markdown으로 목표, 할 일, PRD를 써요. "무엇을, 왜 만드는지"에만 집중해요.
2. **실행·오케스트레이션** — 작성한 태스크를 작업 큐로 넘기고, 에이전트 할당, 상태 전이, 컨텍스트 주입, 예산 관리를 맡겨요.
3. **시각화** — 에이전트 상태(idle, running, blocked)를 받아서 픽셀 아트 캐릭터로 보여줘요.

당시에는 2번 자리에 Paperclip을 넣었어요. 지금 같은 자리에 Multica를 넣으면 무엇이 달라지는지가 이 글의 질문이에요.

## 두 도구를 한 문장으로 요약하면

**Paperclip**은 AI 에이전트로 **회사 하나를 운영하는** 도구예요. 회사(company)를 만들고 목표를 정한 뒤 CEO 에이전트를 고용하면, CEO가 전략을 제안하고 사람이 승인하는 구조예요. 조직도, 보고 라인, 예산, 승인 같은 회사 운영 개념이 그대로 들어 있어요.

**Multica**는 **사람과 에이전트가 한 팀으로 일하는** 작업 공간이에요. 동료에게 이슈를 맡기듯 에이전트에게 이슈를 할당하면, 에이전트가 진행 상황을 댓글로 남기고 결과를 가져와요. 겉보기에는 Linear 같은 이슈 트래커에 에이전트가 팀원으로 들어온 모습에 가까워요.

| 항목        | Paperclip                              | Multica                                   |
| ----------- | -------------------------------------- | ----------------------------------------- |
| 최신 릴리스 | v2026.1012.0 (10월 12일)               | v0.6.4 (10월 20일)                        |
| GitHub 스타 | 약 10.5만                              | 약 5.3만                                  |
| 라이선스    | MIT                                    | Multica License (Apache 2.0 + 추가 조건)  |
| 스택        | TypeScript, Node.js 24+, PostgreSQL    | Go 백엔드, Next.js 웹, PostgreSQL 17      |
| 설치        | `npx paperclipai@latest onboard --yes` | Cloud 가입 또는 `multica setup self-host` |
| 클라이언트  | 웹 보드                                | 웹, 데스크톱(Electron), iOS 앱            |

Paperclip은 `DATABASE_URL`을 비워두면 내장 PostgreSQL로 바로 떠요. 혼자 쓸 때는 로그인 없는 `local_trusted` 모드로 시작하면 돼요. Multica는 Docker Compose나 Helm으로 전체 스택을 올리거나, 관리형 Cloud를 쓰면 돼요. Paperclip Cloud는 아직 대기자 명단(waitlist) 단계예요.

## 일을 시작시키는 방식이 달라요

두 도구의 가장 큰 차이는 **에이전트가 언제 깨어나는가**예요. 이 차이가 비용, 예측 가능성, 쓰는 감각까지 거의 다 결정해요.

### Paperclip: 하트비트로 깨어나요

Paperclip의 에이전트는 **하트비트**(heartbeat)라는 작업 주기 단위로 움직여요. 정해진 일정에 깨어나거나, 티켓 할당 같은 이벤트로 깨어나서 한 사이클을 돌고 다시 쉬어요. 각 사이클은 실행 기록, 사용량, 세션 상태를 남기기 때문에 나중에 추적하기 쉬워요.

5분 시작 가이드도 이 흐름을 그대로 따라가요. 회사를 만들고 CEO를 고용하면 첫 하트비트가 돌고, CEO가 전략 승인 요청을 올려요. 사람이 승인하면 그제야 보드에 첫 태스크들이 생겨요.

### Multica: 명시적인 트리거로만 움직여요

Multica 문서는 에이전트가 **스스로 일을 시작하지 않는다**고 분명히 적어요. 실행은 다음 네 가지 중 하나로만 시작돼요.

1. **이슈 할당** — 이슈를 에이전트에게 맡겨요
2. **@멘션** — 댓글에서 에이전트를 불러요
3. **채팅** — 에이전트와 직접 대화해요
4. **오토파일럿** — 스케줄이나 웹훅으로 반복 작업을 돌려요

다만 "Multica는 하트비트 같은 게 없다"는 말은 이제 맞지 않아요. v0.5.1(9월 21일)에서 댓글이 달리거나 정해진 일정이 되면 이슈가 에이전트를 다시 깨우는 **웨이크업 규칙**이 생겼어요. v0.6.0(9월 28일)에서는 상태 변경, 하위 이슈 완료, PR 변화에 반응하는 **조건부 웨이크업**까지 추가됐어요.

> Paperclip 공식 사이트의 비교 페이지(paperclip.ing/vs/multica)는 Multica에 하트비트 실행이 없다고 적고 있어요. 벤더가 직접 쓴 비교라 이런 최신 변화가 반영되지 않았을 수 있으니, 원문 문서와 함께 보는 게 좋아요.

### @멘션의 의미가 정반대예요

재미있는 차이가 하나 있어요. Paperclip은 v2026.1005.0에서 **@멘션이 더 이상 실행을 시작하지 않도록** 바꿨어요. 이제 멘션은 담당자에게 맥락을 더해줄 뿐이고, 다른 에이전트를 끌어들이려면 태스크를 할당하거나 리뷰를 요청해야 해요.

Multica에서는 반대로 **@멘션이 일을 넘기는 핵심 수단**이에요. 여러 에이전트를 묶은 **스쿼드**(squad)에 이슈를 맡기면 리더 에이전트만 깨어나요. 리더가 맥락을 읽고 댓글에서 적합한 멤버를 @멘션해서 다음 단계를 넘기는 구조예요.

## 돈과 통제는 Paperclip이 훨씬 촘촘해요

에이전트를 여러 개 돌리면 제일 먼저 걱정되는 게 비용이잖아요. 이 부분은 두 도구의 성격 차이가 가장 선명하게 드러나요.

### Paperclip: 예산 상한과 승인이 기본이에요

Paperclip은 회사, 에이전트, 프로젝트 단위로 **예산**을 걸 수 있어요. 경고 임계값을 넘으면 알림이 오고, 상한에 닿으면 에이전트를 **자동으로 일시정지**해요. 대시보드에는 이번 달 지출과 예산 초과 건수가 바로 보여요.

전략 승인, 에이전트 고용 같은 결정은 **승인 큐**를 거쳐요. 모든 변경은 감사 로그(audit log)에 남아서, 무슨 일이 왜 일어났는지 나중에 따라갈 수 있어요.

다만 v2026.1001.0부터 실행 기본값이 **전권 위임**(full-auto)으로 바뀐 점은 알아둬야 해요. Claude는 `approve-all`, Codex는 승인·샌드박스 우회가 기본이에요. Paperclip 자체의 승인 절차는 그대로지만, 도구 단의 승인 게이트가 필요하면 에이전트마다 제한 모드를 직접 설정해야 해요.

### Multica: 비용은 잘 보이지만 상한은 없어요

Multica도 비용 가시성은 꾸준히 좋아지고 있어요. 실행 로그에 실행별 비용 막대와 토큰, 시간, 모델이 표시되고(v0.6.3), 이슈 사이드바에서는 누적 비용 곡선을 볼 수 있어요(v0.6.1). Analytics 페이지에서 지출과 에러 추이도 따로 볼 수 있어요.

하지만 공식 문서와 changelog에서 확인한 범위에서는 **예산 상한이나 지출 기반 자동 일시정지** 기능을 찾지 못했어요. 비용을 "보는" 기능은 있지만, "막는" 기능은 아직 Paperclip 쪽에만 있는 셈이에요.

## 에이전트를 연결하는 방식

### Multica: 내 컴퓨터의 CLI를 그대로 써요

Multica는 서버가 작업을 기록하고 조율하면, 연결된 컴퓨터의 **데몬**이 실행을 가져가서 로컬 AI 코딩 도구를 띄우는 구조예요. 코드, 파일, 그리고 각 도구의 인증 정보는 내 컴퓨터에 남아요. 단, 에이전트의 `custom_env`에 넣은 값은 서버에 저장되니 비밀값은 넣지 않는 게 좋아요.

지원하는 도구는 **26개**나 돼요. Claude Code, Codex, Cursor Agent, GitHub Copilot CLI, OpenCode, Grok, Hermes, Kimi CLI, Qwen Code 같은 도구들이 들어 있어요. 대부분 세션 이어가기와 스킬 주입을 지원해요.

> 2026년 4월에 나온 비교 글들은 Multica가 런타임 8개를 지원한다고 적었어요. 지금 공식 문서 기준으로는 26개라서, 오래된 비교 글은 걸러서 읽는 게 좋아요.

### Paperclip: 어댑터와 커넥터로 넓게 붙여요

Paperclip은 **어댑터**로 에이전트 런타임을 연결해요. Claude Code(`claude_local`), Codex(`codex_local`), Gemini CLI, Cursor, OpenCode, Pi, Hermes, Grok, Kimi Code가 기본으로 들어 있어요. 셸 명령을 감싸는 `process`, 내 서비스를 웹훅으로 부르는 `http` 어댑터도 있어서, 코딩 에이전트가 아닌 것도 "고용"할 수 있어요.

여기에 Paperclip이 자체 실행 수명주기를 관리하는 **네이티브 러너**가 따로 있어요. Daytona 같은 샌드박스 실행도 지원하고요. Slack, GitHub, Railway, Browser Use Cloud 같은 **커넥터**를 권한 단위로 붙일 수 있다는 점도 커요. 코딩 바깥의 업무까지 맡기려면 Paperclip 쪽 선택지가 더 넓어요.

## 최근 릴리스에서 읽히는 방향

changelog를 쭉 읽어보면 두 프로젝트가 어디로 가는지가 보여요.

### Paperclip은 무게를 덜어내는 중이에요

Paperclip에 대한 흔한 비판은 "거버넌스 모델이 복잡하다"는 거였어요. 최근 릴리스는 이 비판에 답하는 방향이에요.

- **기본 지침 대폭 축소** — v2026.1012.0에서 CEO 기본 지침이 약 1,900단어에서 20단어로 줄었어요. 기본 계획 스킬도 400단어 수준으로 가벼워졌어요.
- **채팅 중심 화면** — Agent Chat이 내비게이션 맨 앞으로 왔어요. Inbox와 태스크 목록을 합치는 실험 설정도 생겼어요.
- **외부 에이전트 연결(실험)** — Claude Code, Codex 같은 MCP 클라이언트가 사용자 권한으로 Paperclip에 접속해 태스크를 만들고, 서명된 이벤트 웹훅을 받을 수 있어요.
- **스킬 관리** — GitHub 저장소에서 스킬 폴더를 가져와 동기화하고, 에이전트가 직접 회사 스킬을 고칠 수 있어요.

대신 업그레이드 부담은 커요. 최근 10개 릴리스 중 7개가 **호환성을 깨는 변경**(breaking)으로 표시돼 있거든요. 매번 마이그레이션 노트를 읽고 올리는 습관이 필요해요.

### Multica는 팀 협업 도구로 다듬어지는 중이에요

Multica의 최근 릴리스는 큰 구조 변경보다 협업 경험을 다듬는 쪽이에요.

- **웨이크업 고도화** — 댓글, 일정, 상태 변경, PR 변화에 반응해요
- **비용 가시성** — 실행별, 이슈별 비용을 한눈에 볼 수 있어요
- **협업 편의** — 마크다운 표 정렬·필터, Cmd/Ctrl+K 워크스페이스 전환, 댓글 고유 링크가 생겼어요
- **연동 확장** — Slack, Telegram, Lark, DingTalk 채널과 GitHub, GitLab, Gitea, Forgejo 저장소를 붙일 수 있어요

## 라이선스는 꼭 원문을 확인하세요

Paperclip은 단순한 **MIT 라이선스**예요. 가져다 고쳐 쓰고, 서비스로 만들어 팔아도 돼요.

Multica는 GitHub에서 라이선스가 `NOASSERTION`으로 표시되고, 일부 비교 사이트는 "라이선스 조건이 공개되지 않았다"고 적어요. 하지만 저장소의 LICENSE 파일을 열어보면 **Apache 2.0에 추가 조건을 붙인 Multica License**라는 게 분명히 나와 있어요.

1. **조직 내부 사용은 자유** — 여러 워크스페이스를 써도 상업 라이선스가 필요 없어요
2. **외부 대상 호스팅은 제한** — 제3자에게 Multica를 서비스로 제공하려면, 무료라도 상업 라이선스가 필요해요
3. **UI 브랜딩 유지** — Multica UI를 쓰면 로고, 제품명, 저작권 표시를 지우거나 바꿀 수 없어요

혼자 쓰거나 팀 내부에서 쓰는 데는 문제가 없어요. 하지만 Multica를 기반으로 서비스를 만들 생각이라면 이 조건이 결정적인 차이가 될 수 있어요.

## 3월 역할 분담에 다시 대입해보면

처음에 세운 세 역할에 두 도구를 대입해보면 이렇게 정리돼요.

| 역할                | Paperclip                                              | Multica                                                  |
| ------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| 문서 → 작업 연결    | REST API, MCP 연결(실험)로 태스크 생성·위임            | `multica issue` CLI로 이슈 생성, JSON 출력 지원          |
| 실행·오케스트레이션 | 하트비트, 조직도, 예산, 승인으로 회사 단위 운영        | 이슈 할당, 스쿼드, 웨이크업, 오토파일럿으로 팀 단위 운영 |
| 상태 시각화         | 서명된 이벤트 웹훅으로 받기(실험, HTTPS 공개 URL 필요) | CLI나 API를 주기적으로 조회(폴링)                        |

시각화 쪽은 차이가 꽤 커요. Paperclip은 이벤트를 밀어주는 웹훅이 생겼지만 아직 실험 기능이에요. Multica는 공식 문서와 changelog에서 확인한 범위에서는 **바깥으로 이벤트를 보내는 웹훅**이 없어요. Multica의 웹훅은 오토파일럿을 시작시키는 들어오는 쪽 트리거예요.

그래서 픽셀 아트 대시보드를 붙인다면, Multica에서는 `--output json`으로 상태를 주기적으로 읽어오는 브릿지를 만드는 게 현실적이에요.

```bash
# Multica: 이슈 목록을 JSON으로 받아 대시보드 브릿지에서 가공해요
multica issue list --output json
```

## 어떤 걸 고르면 좋을까

정답은 없지만, 이렇게 나눠보면 고르기 쉬워요.

**Paperclip이 맞는 경우**

- 에이전트를 여러 명 두고 **역할과 보고 라인**까지 설계하고 싶을 때
- **예산 상한과 자동 정지**가 꼭 필요할 때
- 코딩 말고도 Slack, 배포, 브라우저 작업 같은 업무를 맡기고 싶을 때
- MIT 라이선스로 자유롭게 고치고 서비스로 만들고 싶을 때

**Multica가 맞는 경우**

- 사람 팀원과 에이전트가 **같은 이슈 보드에서 함께** 일해야 할 때
- 이미 쓰는 코딩 CLI를 그대로, 내 컴퓨터에서 돌리고 싶을 때
- 데스크톱, 모바일 앱과 채팅 채널로 어디서든 작업을 확인하고 싶을 때
- 큰 구조 변경보다 작은 개선이 자주 쌓이는 도구가 좋을 때

3월 메모의 핵심은 "실행은 맡기고 우리는 문서에 집중한다"였어요. 그 원칙은 어느 도구를 고르든 그대로예요. 내가 원하는 게 **회사를 운영하는 감각**인지, **팀에 동료를 들이는 감각**인지부터 정해보세요. 그 답이 나오면 도구는 자연스럽게 따라와요.

참고로 저는 지금 Multica를 쓰고 있어요.
