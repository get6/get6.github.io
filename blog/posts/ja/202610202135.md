[前回の記事](/posts/202610181853)で、エージェントが働く様子を見守る画面を設計してみた話をしました。それより前の2026年3月に、残しておいたメモがあります。実行エンジンを自前で育てる代わりに、**実行とオーケストレーションはPaperclipに任せ**、自分たちはObsidianでドキュメントを書くことに集中しよう、という内容でした。

それから7か月の間に、Paperclipも、似たポジションを狙うMulticaも大きく変わりました。どちらもほぼ毎週リリースを出しているんです。そこで、当時決めた基準で2つのツールを一から比べ直してみました。

> この記事の数値と機能は**2026年10月20日**時点のものです。どちらのプロジェクトも変化が速いので、導入前には下の参考リンクにある最新のchangelogを必ず確認してください。

## 3月のメモで決めた役割分担

メモではシステムを3つの役割に分けていました。今回の比較も、この3つを基準にしています。

1. **企画・ドキュメント化** — ObsidianでMarkdownを使って目標、タスク、PRDを書きます。「何を、なぜ作るのか」だけに集中します。
2. **実行・オーケストレーション** — 書いたタスクを作業キューに渡し、エージェントの割り当て、状態遷移、コンテキスト注入、予算管理を任せます。
3. **可視化** — エージェントの状態（idle、running、blocked）を受け取り、ピクセルアートのキャラクターで表示します。

当時は2番の枠にPaperclipを入れていました。同じ枠に今Multicaを入れたら何が変わるのか、というのがこの記事の問いです。

## 2つのツールを一言でまとめると

**Paperclip**は、AIエージェントで**会社をひとつ運営する**ためのツールです。会社（company）を作って目標を決め、CEOエージェントを雇うと、CEOが戦略を提案し、人間が承認する仕組みです。組織図、レポートライン、予算、承認といった会社運営の概念がそのまま入っています。

**Multica**は、**人とエージェントがひとつのチームとして働く**ワークスペースです。同僚に頼むようにエージェントにIssueを割り当てると、エージェントが進捗をコメントで残し、成果を持ってきます。見た目は、LinearのようなIssueトラッカーにエージェントがチームメンバーとして加わった姿に近いです。

| 項目         | Paperclip                              | Multica                                      |
| ------------ | -------------------------------------- | -------------------------------------------- |
| 最新リリース | v2026.1012.0（10月12日）               | v0.6.4（10月20日）                           |
| GitHubスター | 約10.5万                               | 約5.3万                                      |
| ライセンス   | MIT                                    | Multica License（Apache 2.0 + 追加条件）     |
| スタック     | TypeScript、Node.js 24+、PostgreSQL    | Goバックエンド、Next.js Web、PostgreSQL 17   |
| インストール | `npx paperclipai@latest onboard --yes` | Cloudに登録、または`multica setup self-host` |
| クライアント | Webボード                              | Web、デスクトップ（Electron）、iOSアプリ     |

Paperclipは`DATABASE_URL`を空のままにしておくと、組み込みPostgreSQLですぐに起動します。一人で使うなら、ログイン不要の`local_trusted`モードから始めれば大丈夫です。MulticaはDocker ComposeやHelmでスタック全体を立ち上げるか、マネージドのCloudを使えばOKです。Paperclip Cloudはまだウェイトリストの段階です。

## 仕事を始めさせる方法が違います

2つのツールの一番大きな違いは、**エージェントがいつ目覚めるか**です。この違いが、コスト、予測しやすさ、使い心地までほとんどを決めます。

### Paperclip：ハートビートで目覚めます

Paperclipのエージェントは、**ハートビート**（heartbeat）と呼ばれる作業サイクル単位で動きます。決まったスケジュールか、チケットの割り当てのようなイベントで目覚め、1サイクル回してまた休みます。各サイクルは実行記録、使用量、セッション状態を残すので、あとから追跡しやすいです。

5分スタートガイドもこの流れをそのままなぞります。会社を作ってCEOを雇うと最初のハートビートが走り、CEOが戦略の承認リクエストを出します。人間が承認して、ようやくボードに最初のタスクが現れます。

### Multica：明示的なトリガーでしか動きません

Multicaのドキュメントには、エージェントは**自分から仕事を始めない**とはっきり書かれています。実行は次の4つのどれかでしか始まりません。

1. **Issueの割り当て** — エージェントにIssueを任せます
2. **@メンション** — コメントでエージェントを呼びます
3. **チャット** — エージェントと直接会話します
4. **オートパイロット** — スケジュールやWebhookで定期的な作業を回します

ただし、「Multicaにはハートビートのようなものがない」という話は、もう正しくありません。v0.5.1（9月21日）で、コメントが付いたときや決めたスケジュールでIssueがエージェントを再び起こす**ウェイクアップルール**が入りました。v0.6.0（9月28日）では、状態変更、サブIssueの完了、PRの変化に反応する**条件付きウェイクアップ**まで追加されています。

> Paperclip公式サイトの比較ページ（paperclip.ing/vs/multica）には、Multicaにはハートビート実行がないと書かれています。ベンダー自身が書いた比較なので、こうした最近の変化が反映されていない可能性があります。元のドキュメントと合わせて読むのがおすすめです。

### @メンションの意味が正反対です

面白い違いがひとつあります。Paperclipはv2026.1005.0で、**@メンションではもう実行が始まらない**ように変えました。今のメンションは担当者にコンテキストを足すだけで、別のエージェントを巻き込むには、タスクを割り当てるかレビューを依頼する必要があります。

Multicaでは逆に、**@メンションが仕事を引き継ぐ中心的な手段**です。複数のエージェントをまとめた**スクワッド**（squad）にIssueを任せると、リーダーエージェントだけが目覚めます。リーダーがコンテキストを読み、コメントで適切なメンバーを@メンションして次のステップを渡す仕組みです。

## お金と統制はPaperclipのほうがずっと細かいです

エージェントを何体も動かすと、まず気になるのはコストですよね。ここで2つのツールの性格の違いが一番はっきり出ます。

### Paperclip：予算上限と承認が標準です

Paperclipでは、会社、エージェント、プロジェクト単位で**予算**を設定できます。警告のしきい値を超えると通知が来て、上限に達するとエージェントを**自動で一時停止**します。ダッシュボードには、今月の支出と予算超過の件数がすぐに表示されます。

戦略の承認やエージェントの採用といった判断は、**承認キュー**を通ります。すべての変更は監査ログ（audit log）に残るので、何がなぜ起きたのかをあとから追えます。

ただし、v2026.1001.0から実行のデフォルトが**フルオート**（full-auto）に変わった点は知っておく必要があります。Claudeは`approve-all`、Codexは承認とサンドボックスのバイパスがデフォルトです。Paperclip自体の承認プロセスはそのままですが、ツール側の承認ゲートが必要なら、エージェントごとに制限モードを自分で設定しなければなりません。

### Multica：コストはよく見えますが、上限はありません

Multicaもコストの可視化は着実に良くなっています。実行ログには実行ごとのコストバーとトークン、時間、モデルが表示され（v0.6.3）、Issueのサイドバーでは累積コストの曲線を見られます（v0.6.1）。Analyticsページでは、支出とエラーの推移も別々に確認できます。

ただ、公式ドキュメントとchangelogで確認した範囲では、**予算上限や支出ベースの自動一時停止**の機能は見つかりませんでした。コストを「見る」機能はあっても、「止める」機能は今のところPaperclipにしかない、ということです。

## エージェントのつなぎ方

### Multica：自分のPCのCLIをそのまま使います

Multicaは、サーバーが作業を記録・調整し、接続されたコンピューターの**デーモン**が実行を引き取ってローカルのAIコーディングツールを起動する仕組みです。コード、ファイル、各ツールの認証情報は自分のPCに残ります。ただし、エージェントの`custom_env`に入れた値はサーバーに保存されるので、秘密情報は入れないほうがいいです。

対応ツールは**26個**もあります。Claude Code、Codex、Cursor Agent、GitHub Copilot CLI、OpenCode、Grok、Hermes、Kimi CLI、Qwen Codeといったツールが含まれます。ほとんどがセッションの再開とスキルの注入に対応しています。

> 2026年4月に出た比較記事では、Multicaの対応ランタイムは8個とされていました。今の公式ドキュメントでは26個なので、古い比較記事は割り引いて読むのがいいです。

### Paperclip：アダプターとコネクターで幅広くつなぎます

Paperclipは**アダプター**でエージェントのランタイムをつなぎます。Claude Code（`claude_local`）、Codex（`codex_local`）、Gemini CLI、Cursor、OpenCode、Pi、Hermes、Grok、Kimi Codeが標準で入っています。シェルコマンドをラップする`process`、自分のサービスをWebhookで呼ぶ`http`アダプターもあるので、コーディングエージェントではないものまで「雇う」ことができます。

さらに、Paperclipが独自に実行ライフサイクルを管理する**ネイティブランナー**が別にあり、Daytonaのようなサンドボックスでの実行にも対応しています。Slack、GitHub、Railway、Browser Use Cloudといった**コネクター**を権限単位で付けられるのも大きいです。コーディング以外の業務まで任せたいなら、Paperclipのほうが選択肢は広いです。

## 最近のリリースから読み取れる方向性

changelogを通して読むと、2つのプロジェクトがどこへ向かっているかが見えてきます。

### Paperclipは重さを削っています

Paperclipによくある批判は「ガバナンスモデルが複雑だ」というものでした。最近のリリースは、この批判に応える方向です。

- **デフォルト指示の大幅な削減** — v2026.1012.0で、CEOのデフォルト指示が約1,900語から20語に減りました。標準の計画スキルも400語程度まで軽くなっています。
- **チャット中心の画面** — Agent Chatがナビゲーションの先頭に来ました。Inboxとタスク一覧をまとめる実験的な設定も加わっています。
- **外部エージェントとの接続（実験的）** — Claude CodeやCodexのようなMCPクライアントが、ユーザーの権限でPaperclipに接続し、タスクを作ったり、署名付きのイベントWebhookを受け取ったりできます。
- **スキル管理** — GitHubリポジトリからスキルフォルダを取り込んで同期でき、エージェントが会社のスキルを直接更新することもできます。

その代わり、アップグレードの負担は大きいです。直近10リリースのうち7つが**互換性を壊す変更**（breaking）として表示されています。毎回マイグレーションノートを読んでから上げる習慣が必要です。

### Multicaはチームコラボツールとして磨かれています

Multicaの最近のリリースは、大きな構造変更よりも、コラボレーション体験を磨く方向です。

- **ウェイクアップの強化** — コメント、スケジュール、状態変更、PRの変化に反応します
- **コストの可視化** — 実行ごと、Issueごとのコストがひと目でわかります
- **コラボの使いやすさ** — Markdownの表の並べ替え・フィルター、Cmd/Ctrl+Kでのワークスペース切り替え、コメントのパーマリンクが加わりました
- **連携の拡大** — Slack、Telegram、Lark、DingTalkのチャンネルと、GitHub、GitLab、Gitea、Forgejoのリポジトリをつなげます

## ライセンスは必ず原文を確認してください

Paperclipはシンプルな**MITライセンス**です。持ってきて改造しても、サービスにして販売しても大丈夫です。

MulticaはGitHub上でライセンスが`NOASSERTION`と表示され、一部の比較サイトは「ライセンス条件が公開されていない」と書いています。でも、リポジトリのLICENSEファイルを開くと、**Apache 2.0に追加条件を付けたMultica License**だとはっきり書かれています。

1. **組織内での利用は自由** — 複数のワークスペースを使っても、商用ライセンスは不要です
2. **外部向けホスティングは制限あり** — 第三者にMulticaをサービスとして提供するには、無料でも商用ライセンスが必要です
3. **UIのブランディングは維持** — Multica UIを使うなら、ロゴ、製品名、著作権表示を消したり変えたりできません

一人で使ったり、チーム内で使ったりする分には問題ありません。でも、Multicaをベースにサービスを作るつもりなら、この条件が決定的な違いになり得ます。

## 3月の役割分担にもう一度当てはめてみると

最初に決めた3つの役割に2つのツールを当てはめると、こう整理できます。

| 役割                       | Paperclip                                                     | Multica                                                                       |
| -------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| ドキュメント → タスク連携  | REST API、MCP接続（実験的）でタスクを作成・委任               | `multica issue` CLIでIssueを作成、JSON出力に対応                              |
| 実行・オーケストレーション | ハートビート、組織図、予算、承認で会社単位の運営              | Issue割り当て、スクワッド、ウェイクアップ、オートパイロットでチーム単位の運営 |
| 状態の可視化               | 署名付きイベントWebhookで受信（実験的、HTTPSの公開URLが必要） | CLIやAPIを定期的に取得（ポーリング）                                          |

可視化の部分は差がかなり大きいです。PaperclipにはイベントをプッシュしてくれるWebhookができましたが、まだ実験的な機能です。Multicaは、公式ドキュメントとchangelogで確認した範囲では**外部へイベントを送るWebhook**がありません。MulticaのWebhookは、オートパイロットを起動するための受信側のトリガーです。

なので、ピクセルアートのダッシュボードをつなぐなら、Multicaでは`--output json`で状態を定期的に読み込むブリッジを作るのが現実的です。

```bash
# Multica：Issue一覧をJSONで受け取り、ダッシュボードのブリッジで加工します
multica issue list --output json
```

## どちらを選べばいいか

正解はありませんが、こう分けてみると選びやすくなります。

**Paperclipが合うケース**

- 複数のエージェントを置き、**役割とレポートライン**まで設計したいとき
- **予算上限と自動停止**が絶対に必要なとき
- コーディング以外にも、Slack、デプロイ、ブラウザ作業といった業務を任せたいとき
- MITライセンスで自由に改造し、サービスにしたいとき

**Multicaが合うケース**

- 人間のチームメンバーとエージェントが**同じIssueボードで一緒に**働く必要があるとき
- すでに使っているコーディングCLIを、そのまま自分のPCで動かしたいとき
- デスクトップやモバイルアプリ、チャットチャンネルからどこでも作業を確認したいとき
- 大きな構造変更より、小さな改善が頻繁に積み重なるツールが好きなとき

3月のメモの核心は「実行は任せて、自分たちはドキュメントに集中する」でした。その原則は、どちらのツールを選んでも変わりません。自分が求めているのが**会社を運営する感覚**なのか、**チームに同僚を迎える感覚**なのかを、まず決めてみてください。その答えが出れば、ツールは自然と決まります。

ちなみに、私は今Multicaを使っています。
